## Learned User Preferences
- User prefers autonomous execution with minimal back-and-forth; for large work, audit then plan then implement in phases without mid-task confirmation unless blocked, and continue until major tasks are complete.
- User often prefers Russian for task instructions and progress communication.
- User values direct, action-oriented progress over extended planning-only responses.
- User frequently asks for deep end-to-end truth-based audits with a single consistent final status, and full hardening/closure rather than partial fixes.
- User prioritizes high-quality, polished outcomes and is comfortable trading speed for quality.
- User expects Supabase project provisioning, migrations, and server-side secrets to be handled via Supabase MCP/server automation rather than manual dashboard or local PAT flows when possible.
- User expects production infrastructure on **hiair.io** via Cloudflare (Pages, Worker proxy, Containers for API)—not Fly.io or other ad-hoc host proposals unless explicitly requested; production deploy via `.github/workflows/backend-deploy-production.yml`; on deploy failures diagnose CI logs before changing code—invalid/expired `CLOUDFLARE_API_TOKEN` is fixed in GitHub `production` env secrets (Account Read + Workers Scripts/Containers Edit), not backend code.
- For mobile login/auth blockers, user expects deep production fixes across iOS, `api.hiair.io`, and Supabase—not superficial UI-only changes.
- For brand or visual redesign work, keep scope to design tokens, components, and assets only; integrate supplied mockups or publish packs for orb, icons, and launch assets without changing backend, API, auth, data models, risk engine, or business flows, and keep UI components presentation-only.
- For subscription and store readiness, use an honest status ladder (ARCHITECTURE READY → STORE SANDBOX READY → PRODUCTION READY); never claim STORE SANDBOX READY without real on-device sandbox purchase verification.
- For health/wearable features, require explicit user consent, store only daily/hourly aggregates (no raw streams), use wellness-only language (no diagnoses or emergency alerts), keep the app fully functional when health permissions are denied, and for iOS HealthKit blockers fix Apple Developer Portal App ID capability, provisioning/signing, Info.plist purpose strings, and real `requestAuthorization` flow—not Settings deep links or UI-only changes.
- For first-10-users/beta readiness, treat it as a quality-hardening sprint (no new features): find → fix → verify → confirm nothing broke before moving on, leave no TODO/FIXME/HACK/dead code/duplication, and give one honest verdict (READY FOR FIRST 10 USERS vs NOT READY); follow P0 ordering backend live data → deploy + production smoke on `api.hiair.io` → device QA → push → internal testing/TestFlight, then RC phases RC-1 production readiness → RC-2 device certification → RC-3 store certification → RC-4 first 10 users; defer Family Mode/Premium/full wearable ingestion/ML/new AI/major UI until RC-1/RC-2 complete; device QA and store uploads must use Release builds on `api.hiair.io` (Debug → localhost); production must never show mock/fake data (mock only in preview/debug/tests).
